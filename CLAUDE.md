# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

A skill-tree and readiness-tracking app, built in phases. `plans/Progession_Tracker_plan.md` is the only source of truth for scope, decisions and the phase list. Read the relevant section before starting a phase. Anything the plan marks as deferred (revision history, tree linking and readiness aggregation, cross-user features) must not be built early. The data model should only be *shaped* to allow it.

Workflow: after finishing a set of changes, stop and ask the user to review them. Commit only after they approve, then ask before starting the next phase.

## Commands

Everything runs from the repo root unless noted. Docker must be running.

```bash
docker compose up -d          # local Postgres 18 on :5432 (db/user/password: progressiontracker)
docker compose down           # stop it (add -v to delete the data volume)

docker compose --profile app up -d --build   # whole app in containers at http://localhost:8081
docker compose --profile app down            # stop it; plain `down` leaves the app containers running

cd backend
./mvnw spring-boot:run                                   # run the API on :8080 against the compose DB
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev    # same, plus hand-written seed data (one dev seeder per module)
./mvnw test                                              # all tests (Testcontainers starts its own Postgres)
./mvnw test -Dtest=ProgressionTrackerBackendApplicationTests            # a single test class
./mvnw test -Dtest=ProgressionTrackerBackendApplicationTests#contextLoads  # a single test method
./mvnw package                                           # build the jar into backend/target/
```

Frontend, from `frontend/` (the backend must be running for `npm start` to show data):

```bash
npm install                                    # first time only
npm start                                      # dev server on :4200; proxies /api to :8080 (proxy.conf.json)
npm test -- --watch=false                      # all Vitest specs, once
npm test -- --watch=false --include src/app/trees/readiness.spec.ts   # a single spec file
npm run build                                  # production build into frontend/dist/
npx playwright install chromium                # first time only: the browser for the e2e tests
npm run e2e                                    # Playwright browser tests against a throwaway Docker stack
npm run e2e -- e2e/trees.spec.ts               # a single browser-test file
```

No linter is configured. The frontend has a Prettier config (`frontend/.prettierrc`); the backend has no formatter.

## Containers (Phase 4b)

`backend/Dockerfile` and `frontend/Dockerfile` are two-stage builds: Maven then a JRE, and Node then nginx. The `backend` and `frontend` Compose services sit behind the `app` profile so plain `docker compose up` stays database-only for development. The backend container gets its database from `SPRING_DATASOURCE_URL`/`_USERNAME`/`_PASSWORD` (Compose fills the login from `POSTGRES_USER`/`POSTGRES_PASSWORD`, defaulting to the local values), reports healthy once `/actuator/health` is `UP` (the frontend and `docker compose up --wait` wait for that), and publishes no port (8080 stays free for `./mvnw spring-boot:run`). `frontend/nginx.conf` forwards `/api` to `backend:8080` and falls back to `index.html` for Angular routes, the same job `proxy.conf.json` does for `npm start`. Image builds skip tests because Testcontainers can't run inside a build.

## CI (Phase 6.0)

GitHub Actions, in `.github/workflows/ci.yml`, on every push to any branch (and by hand). The `backend`, `frontend` and `e2e` jobs run the same commands as locally (`./mvnw -B test`; `npm ci`, `npm test -- --watch=false`, `npm run build`; `npx playwright install --with-deps chromium`, `npm run e2e`). The e2e job uploads the Playwright report and traces when it fails. On `main`, once all three pass, the `images` job builds both Dockerfiles and pushes them to `ghcr.io/xenonreaction/progression-tracker-{backend,frontend}` tagged with the commit SHA and `latest`, using the run's `GITHUB_TOKEN`, then keeps only the latest 10 versions of each. The repository is private and `main` is pushed to directly; a red run is fixed before the next change. Check runs with `gh run list` / `gh run watch`.

## Configuration and health (Phase 6.1)

- `application.properties` holds local defaults only; `SPRING_DATASOURCE_*` environment variables override them. ## Browser tests (Phase 5.0)

Playwright on Chromium only, in `frontend/e2e/`, configured by `frontend/playwright.config.ts`. `e2e/global-setup.ts` runs `docker compose -f e2e/docker-compose.yml` (project `progression-tracker-e2e`: the same Dockerfiles, an in-memory Postgres, the `dev` seed, frontend on port 8090 or `E2E_PORT`), waits for the API, and tears the stack down after the run (`E2E_KEEP_STACK=1` keeps it). - On edit pages, wait for the loaded values (`toHaveValue`) before typing, or the load overwrites what was typed.
- Every sub-phase that changes on-screen behavior adds tests here.

## Layout

- `frontend/`: Angular 22 app built with npm and the Angular CLI, separate from the Maven build. It uses plain Angular with no component library, and UI polish is deliberately deferred. Browser tests are in `frontend/e2e/`.

## Decided technical conventions

- **Persistence:** Spring Data JPA + Hibernate throughout, with no hand-written JDBC layer.
- **Schema (Phase 5.1):** Flyway migrations in `backend/src/main/resources/db/migration/` create and change the schema. They run on startup everywhere (`spring-boot:run`, Docker, Testcontainers tests). Hibernate runs with `ddl-auto=validate` and refuses to start if an entity and the schema disagree. `V1` is the Milestone 1 schema as Hibernate built it. A non-empty database without Flyway's history table is refused (`baseline-on-migrate` was removed in 6.1 after the one pre-Flyway database was baselined), and `MigrationTest` covers both an empty and a refused database. To change the schema, add the next `V<n>__<what_it_does>.sql` and update the entities to match. Never edit a migration that has already run: Flyway checksums them and refuses to start.
- **REST:** every endpoint is under `/api/v1/...`.
- **Tests:** unit tests use JUnit + Mockito (loaded as a Java agent through surefire's `argLine`), with `TestEntities.withId` to set IDs on entities that were never saved. Integration tests run against real Postgres through Testcontainers, never H2 or another in-memory database. Repository tests use `@DataJpaTest`, and `ApiIntegrationTest` drives the whole HTTP stack with `MockMvcTester`, emptying the tables after each test. Test classes that need the database import `TestcontainersConfiguration`, which uses a `@ServiceConnection` `postgres:18` container, the same image as `docker-compose.yml`. `TestProgressionTrackerBackendApplication` runs the app against a throwaway container instead of the compose database.
- **Logging (Phase 6.2):** SLF4J + Logback. `RequestLoggingFilter` gives each request an id (the `requestId` MDC key and `X-Request-Id` header, keeping a caller's plain id) and logs one INFO line per request (method, path, status, ms), skipping `/actuator/**`. Text logs show `[requestId]` after the thread (`logging.pattern.correlation`); the `prod` profile logs ECS JSON. Log important changes at INFO **by id only**: never titles, descriptions or other user text, and never secrets. Expected refusals (`NotFound`/`BadRequest`/`Conflict`/validation) are DEBUG; `ApiExceptionHandler.handleUnexpected` logs anything else at ERROR and returns a generic 500 with `requestId`. Tests assert on log output with `OutputCaptureExtension`.
- `spring.jpa.open-in-view=false`: all database access belongs in the service layer.
- **Schema constraints:** every constraint has a readable name: `<table>_<column>_fk` for foreign keys, `<table>_<columns>_unique`, and names such as `nodes_readiness_range` for checks. The migrations create them, and the entities repeat the names (`@CheckConstraint`, `@UniqueConstraint`, `@ForeignKey`) so the mappings document them. Tests assert on those names. Cascades go through `@OnDelete(CASCADE)` on foreign keys (tree → tree_nodes → prerequisites). Deleting a library `Node` that a tree still uses is refused: `NodeService` returns 409, and the foreign key backs that up.
- **Naming:** a field ending in a single capital letter (e.g. `positionX`) doesn't get an underscore from Spring's naming strategy, so name those columns explicitly. Renaming or dropping a column is a migration, not a database reset.
- **Enums:** store them as lowercase strings through an `AttributeConverter` (see `NodeResourceTypeConverter`), with a check constraint listing the allowed values. Adding a value means a migration that widens the check.

## Backend structure

**Modules (Phase 7.1):** a modular monolith. Each top-level package under `com.progressiontracker` is a Spring Modulith module: `progression` (subpackages `node`, `tree`, `readiness`, `seed`), `flashcards`, `materials`, `lessons`, `coding`, `user`, `common` (exception types and `ApiExceptionHandler`) and `config`. A module may use only another module's top-level package (its public API), never its subpackages, and modules may not depend on each other in a circle. `ModularityTest` (`ApplicationModules.verify()`, test scope only) fails the build otherwise. Learning modules own their own records and refer to other modules' rows by plain id, with no foreign keys between them (the shared `users` table is the exception). When a module must stop another deleting something it refers to, the owner declares a check interface in its API and the other module implements it (`DeckDeletionCheck`, `MaterialDeletionCheck`, `LessonDeletionCheck`, `QuestionSetDeletionCheck`, implemented by the matching `Node…DeletionCheck` in `progression.node`), so dependencies still point one way: `progression` → the learning modules. Within a module, code is organized by feature, each with its own entities, repositories, services, controllers and request/response records.

- **Flashcards (Phase 7.1):** `flashcards` exposes only `FlashcardReadinessCalculator` (with `deck(Long)`, how other modules read one of the user's decks as a `DeckSummary`), its `CardProgress`/`DeckProgress` records and `DeckDeletionCheck`; everything else is in `flashcards.internal`. The rules live in those records: a card has passed when the user's last `PASS_STREAK` (3) answers were all correct, a deck's readiness is the share of its cards passed (rounded, 0 when empty), and it's complete at `COMPLETE_PERCENT` (80) of the exact share. **Spaced repetition (Phase 7.7):** a passed card is due again after a fixed interval from its last answer, growing with the correct answers in a row (`CardProgress.intervalAfter`: 7 days at 3, then 14, 30, and 60 from then on); a wrong answer un-passes it. Cards carry `dueAt` and `due`, decks a `dueCount`; being due never changes readiness. Progress and due dates are computed from `card_reviews` when read, never stored, and every answer is kept. "Now" comes from the `Clock` bean (`common.ClockConfiguration`); tests replace it with `TestClock` (import `TestClock.Config`, then `advance`). Endpoints: `/api/v1/decks` (CRUD), `/api/v1/decks/{id}/cards` (CRUD), `POST .../cards/{cardId}/reviews` (`{correct}`, returns the card's new standing) and `GET /api/v1/review-queue[?deckId=]` (cards not passed and passed cards that are due, never-answered first, then the least recently answered). Deleting a deck cascades to its cards and their reviews, and is refused (409 with a `nodes` list) while a node lists it.

- **Materials (Phase 7.4):** `materials` exposes `MaterialReadinessCalculator` (`material(Long)` returns a `MaterialSummary`: title, latest reported progress, when) and `MaterialDeletionCheck`; everything else is in `materials.internal`. A `Material` is a URL (http(s)) with a title and notes. Each `MaterialProgressUpdate` (progress 0–100, note, `recordedAt`) is kept forever; the latest is the material's progress (0 if none) and its time is "last reviewed". Editing a material's details isn't a review. Endpoints: `/api/v1/materials` (CRUD), `GET .../{id}/progress` (history, newest first) and `POST .../{id}/progress` (`{progress, note}`, returns the material). Deleting cascades to the history, and is refused (409 with `nodes`) while a node lists it.
- **Lessons (Phase 7.5):** `lessons` exposes `LessonReadinessCalculator` (`lesson(Long)` returns a `LessonSummary`: title, latest progress entered, last opened) and `LessonDeletionCheck`; everything else is in `lessons.internal`. A `Lesson` has a title, optional summary and ordered `LessonSection`s (heading and Markdown body, an `@ElementCollection` in `lesson_sections`). The user's activity is kept per user: `LessonOpen` (each time the lesson page is opened; the latest is "last reviewed") and `LessonProgressUpdate` (the latest is its progress, 0 if none); `LessonActivity` records and reads both. `GET /api/v1/lessons/{id}` has no side effects, so the edit form doesn't count as a review; the lesson page calls `POST .../{id}/opens`, which returns the lesson. Also `/api/v1/lessons` (CRUD) and `POST .../{id}/progress` (`{progress}`). Deleting cascades to sections and activity, and is refused (409 with `nodes`) while a node lists it.
- **Coding practice (Phase 7.6):** `coding` exposes `QuestionSetReadinessCalculator` (`questionSet(Long)` returns a `QuestionSetSummary` with a `SetProgress`), the `QuestionProgress`/`SetProgress` records (the rules: a question counts once marked solved, a set is the share solved, rounded, 0 when empty) and `QuestionSetDeletionCheck`; everything else is in `coding.internal`. A `QuestionSet` holds `CodingQuestion`s (title, `CodingLanguage` `html`/`css` (JavaScript later, by widening `coding_questions_language_check`), Markdown problem and examples, and a solution). Attempts are `QuestionAttempt`s per user, `revealed` or `solved`; `revealedBeforeSolved` is recorded but doesn't change readiness yet. The solution is left out of responses until revealed: `POST .../reveal` records it and returns it; `GET .../questions/{id}?includeSolution=true` (the edit form) returns it without recording. No code runs on the server. Endpoints: `/api/v1/question-sets` (CRUD) and `/api/v1/question-sets/{setId}/questions` (CRUD, `POST .../{id}/reveal`, `POST .../{id}/solved`). Deleting a set cascades to its questions and attempts, and is refused (409 with `nodes`) while a node lists it.
- **Node resources (Phases 7.2 to 7.6):** a node's `resources` (`NodeResource`, an `@ElementCollection` in `node_resources`, ordered by `position`) are what it points to: `NodeResourceType.URL` (a URL, never counts), `TREE` (a tree, by foreign key `tree_id`), `DECK` (a flashcard deck), `MATERIAL` (an external material), `LESSON` or `QUESTION_SET` (coding questions), the last four by plain id in `target_id` with no foreign key. All but URLs count unless marked reference-only. Each has an optional `label`; null means show the target's title. `NodeService` checks each one (400 for a wrong shape, a URL that counts, an unknown type or a target listed twice; 404 for a target that isn't the user's, those in other modules confirmed through the module's API). `@CollectionTable` can't declare checks, so the `node_resources_*` check constraints are only in the migrations (V7, widened in V8 to V11). Requests carry `resources` as `{type, url|treeId|deckId|materialId|lessonId|questionSetId, label, counts}`; responses as `{type, url, tree, deck, material, lesson, questionSet, label, counts, readiness, lastReviewedAt, reviewDue}`, where `readiness`, `lastReviewedAt` and `reviewDue` are the resource's own (null for a URL), counting or not.
- **Readiness (Phases 5.2, 7.2 and 7.3):** readiness and "last reviewed" are computed when read, never stored. A node's readiness is the plain average of its resources that count, rounded to a whole percent, or its hand-entered value when none count; its `lastReviewedAt` is the latest review beneath the resources that count (null when none, or when nothing counts), and its `reviewDue` whether any of them has a flashcard due (Phase 7.7; only decks have a schedule so far). A tree's readiness is the average of its nodes' (0 when empty), its `lastReviewedAt` the latest of theirs, and its `reviewDue` whether any of them has one; `TreeResponse` and `TreeNodeResponse` carry all three. `ReadinessService.context()` gives a `ReadinessContext` for one request (it caches node, tree and resource results, and loads trees lazily, so use it inside the service transaction). For each resource the context asks the `ReadinessCalculator` for its type, which returns a `ResourceStatus` (title, readiness, last reviewed, review due): `TreeResourceReadinessCalculator` averages the tree's nodes (recursively), `DeckResourceReadinessCalculator` asks the Flashcards module's `FlashcardReadinessCalculator.deck(id)`, `MaterialResourceReadinessCalculator` the Materials module's `MaterialReadinessCalculator.material(id)`, `LessonResourceReadinessCalculator` the Lessons module's `LessonReadinessCalculator.lesson(id)`, and `QuestionSetResourceReadinessCalculator` the Coding module's `QuestionSetReadinessCalculator.questionSet(id)`. A type that can count (`NodeResourceType.canCount()`) must have a calculator, or `ReadinessService` refuses to start; a new type adds an enum value, a calculator and a migration widening `node_resources_resource_type_check`. Responses carry the effective `readiness`; `NodeResponse` also has `manualReadiness`, and the hand-entered value is set with `PUT /nodes/{id}/readiness` only while nothing counts (409 otherwise).
- **Tree links:** `TreeLinks.checkNoLoop` refuses (409) a link that would make a tree's readiness depend on itself. It runs for each tree a node counts, when a node's resources are saved (`NodeService`) and when a node is placed in a tree (`TreeNodeService.add`). A reference-only tree resource can't make a loop, so it isn't checked. A tree that any node lists as a resource, counting or not, can't be deleted (`TreeService.delete`, 409 with a `nodes` list).
- **Edit sessions (Phase 5.3a):** `TreeEditSessionService` backs a tree's edit mode. `start` saves a `TreeSnapshot` (details, placements by library node id, thresholds, edges by library node ids) as JSON in `tree_edit_sessions`, one per tree (409 if one exists). Edits are still saved as they're made. `finish` ("Done") deletes the session. `discard` restores the snapshot, matching placements by library node id: it re-places removed nodes, removes added ones, rebuilds every edge, and deletes library nodes created since the session started that end up in no tree. `TreeResponse.editSessionStartedAt` shows a session is open. The backend doesn't refuse edits outside a session; view mode is enforced by the UI.

- **Current user:** `CurrentUserService.getCurrentUser()` is the only way code finds out who the user is. In v1 it returns (and creates on first use) the user named by `progressiontracker.default-username`. When authentication is added, only this class should change. Every lookup is scoped to the owner (`findByIdAndOwner`, `TreeService.findOwned`, `TreeNodeService.findInTree`), and a resource owned by someone else returns 404, not 403.
- **Services return DTOs:** entities never leave the service layer. Because `open-in-view` is off, mapping to response records has to happen inside the service transaction, where lazy associations can still load. Update methods call `flush()` before mapping so `updatedAt` is current.
- **Errors:** throw `NotFoundException` (404), `BadRequestException` (400) or `ConflictException` (409, with optional extra properties such as the `trees` list when a node delete is refused). `ApiExceptionHandler` turns them into `ProblemDetail`, and bean-validation failures come back with an `errors` list of `{field, message}`. Database constraint violations are a 409 backstop, not the main way rules are checked.
- **Edges:** `PrerequisiteService` checks self-edges, same-tree membership, duplicates and cycles (`PrerequisiteGraph`) in that order. An edge's only editable field is its `route` (Phase 5.4): an `EdgeRoute` (`segments` 3 or 5, and one offset per draggable segment) stored as JSON text through `EdgeRouteConverter`, or null for the default route. The backend only checks its shape (`EdgeRoute.check`); the geometry lives in the frontend. `PUT .../prerequisites/{id}/route` sets one, `DELETE .../prerequisites/routes` resets all of them, and edit-session snapshots include routes.

## Frontend structure

Standalone components, zoneless change detection, signals for state, reactive forms, and the 2025 file naming (`node-list.ts`, not `node-list.component.ts`).

- `core/`: `api.models.ts` mirrors the backend's response and request records and must be kept in sync with them by hand. `NodeApi`, `TreeApi`, `FlashcardApi`, `MaterialApi`, `LessonApi` and `CodingApi` are thin `HttpClient` wrappers using relative `/api/v1` URLs. `problem.ts` turns problem responses into messages. `markdown.ts` (`renderMarkdown`, the `marked` package) turns lesson and question Markdown into HTML for `[innerHTML]`, which Angular sanitizes. `test-data.ts` has `aNode()`/`aTreeNode()`/`aDeck()`/`aCard()`/`aMaterial()`/`aLesson()`/`aQuestionSet()`/`aCodingQuestion()` and resource builders for specs.
- `nodes/`: the library list, `NodeView` (`/nodes/:id`, the node's read-only page with its resources grouped by type (trees, decks, links) with each one's readiness, tags, the trees using it and its readiness), `ReadinessBreakdown` (what a derived readiness is made of, e.g. "Deck Flexbox cards: 75%, Material Guide: 60% (self-reported) → 68%", and "Last reviewed"; used on the node page and in the tree editor's details), and the create/edit form. `ReadinessEditor` updates hand-entered readiness in place (`PUT /nodes/{id}/readiness`) and is used on both view pages while nothing counts; it's the only change view mode allows. The form covers title, description, tags and resources: "+ Add link", "+ Add tree", "+ Add deck", "+ Add material" and "+ Add lesson" rows (plus "+ Add question set"), each with a label, move up/down and remove, and a "Counts toward readiness" checkbox on all but links (ticked for a new one); a row with no target chosen says "Choose a …". Each row binds its own `FormGroup` with `[formGroup]`, not `formGroupName="i"`, which wouldn't follow a moved row. Each type's list of targets loads when the first row of that type appears. The form doesn't edit the hand-entered value but always sends it back, so un-counting restores it. It honours a `returnTo` query param, restricted to in-app paths, and otherwise returns to the node's page. `resources.ts` holds the pure helpers (`resourceTitle`, `resourceLink`, `isSelfReported` (materials and lessons), `countingResources`, `readinessSources`, `titleList`, `RESOURCE_GROUPS`).
- `flashcards/` (Phase 7.1): `DeckList` (`/decks`), `DeckForm`, `DeckView` (`/decks/:id`: readiness, and the cards, added and edited in place with `CardForm`), `DeckStudy` (`/decks/:id/study`: the deck's review queue, or every card once all have passed) and `ReviewPage` (`/review`: the review queue across decks). Both study pages use `StudySession`, which shows a card's front, reveals the back and records the user's own verdict, then ends with a summary and "Study again". `card-status.ts` holds the status wording and mirrors the backend's `PASS_STREAK` and `COMPLETE_PERCENT`. Due reviews (Phase 7.7) show as a count on the deck list and page, a "Next review" column on the deck page, and "Review due" (class `review-due`) on the node list and page, in `ReadinessBreakdown`, on the tree list and page, and as a `review-due-marker` on tree canvas nodes.
- `materials/` (Phase 7.4): `MaterialList` (`/materials`), `MaterialForm` (details only) and `MaterialView` (`/materials/:id`: the link, notes, progress marked "self-reported", a form to report new progress that starts from the last value, and the full history).
- `lessons/` (Phase 7.5): `LessonList` (`/lessons`), `LessonForm` (title, summary and sections, each row bound with `[formGroup]`, add, move and remove) and `LessonView` (`/lessons/:id`: records an open on load and shows the response, renders each section's Markdown with `renderMarkdown`, and a progress form marked "self-reported").
- `coding/` (Phase 7.6): `QuestionSetList` (`/question-sets`), `QuestionSetForm`, `QuestionSetView` (`/question-sets/:id`: readiness and each question's status from `question-status.ts`), `QuestionForm` (`.../questions/new` and `.../:questionId/edit`; loads with `includeSolution=true`) and `QuestionView` (`.../questions/:questionId`: problem and examples as Markdown, "Mark solved", and "Show solution", which confirms that seeing it is recorded).
- **Lazy routes:** the node and tree pages load with the app; the learning modules' pages (flashcards, materials, lessons, coding) use `loadComponent`, which keeps the initial bundle under the 500 kB budget and `marked` out of it.
- `trees/`: the tree list (with each tree's readiness and last review), `TreeForm` for tree metadata CRUD (Phase 3b; comma-separated tags parsed in `tags.ts`), and `TreeView`, the tree editor. `TreeView` draws an inline SVG of boxes centred on the stored positions, shows the tree's own readiness under its title, marks nodes whose readiness comes from resources ("linked"), and loads its data from an `effect` on `id()`, because "Open linked tree" reuses the component for another tree. `readiness.ts` (the readiness levels), `tree-layout.ts` (view box and edge geometry) and `auto-layout.ts` (layered layout) are pure functions with their own specs.
- **View and edit modes (Phase 5.3a):** `TreeView` opens in view mode: clicking a node shows its details, resources and a `ReadinessEditor` (or its `ReadinessBreakdown`, linking to each tree and deck), and nothing can be dragged. "Edit" starts an edit session; "Done" and "Discard changes" end it. The route's `canDeactivate` calls `TreeView.canLeave`, which lets edit mode go to the tree's own details form (opened with `?resumeEdit=true`, so `TreeForm` returns into the session) and otherwise confirms, then discards. `beforeunload` triggers the browser's own warning. A session found on load without `resumeEdit` is unfinished: a banner asks "Keep" (finish) or "Discard" before anything else.
- **Undo and redo (Phase 5.3b):** every edit in the tree editor records an `EditCommand` (`trees/edit-commands.ts`) in the page's `UndoHistory` (`trees/undo-history.ts`, 50 steps, a new change clears redo), once its save succeeds. Undo and redo are saved to the server like any edit, then the tree reloads. Commands name nodes by library node id, never tree node id, and resolve the current placement through the `EditContext` when they run, because undoing a removal re-places a node under a new tree node id. Undoing "create and place" deletes the library node unless another tree uses it, and redo recreates it under a new id, recorded as an alias. A failed undo or redo shows the error and clears the history. Ctrl+Z undoes and Ctrl+Y or Ctrl+Shift+Z redoes, except while typing in a field. The history ends with the edit session. To make a new kind of edit undoable, add a command factory and call `record()` after the save succeeds.
- **Right-angle edges (Phase 5.4):** `trees/edge-routes.ts` (pure, with its spec) routes each edge from the prerequisite's bottom-middle port to the dependent's top-middle port: 3 segments (down, across, down) when the dependent is at least `2 * STUB` below, otherwise 5 (down, out to the right of both nodes, up, across, down). A stored route is applied only if it has the same number of segments, and its offsets are clamped so segments stay between the ports. Stored offsets are relative to the default route, so a node move keeps an adjustment. In edit mode with the select tool, each draggable segment has a `segment-handle` line; dragging one previews through `routeOverrides` and saves the clamped result. A move that changes an edge's segment count resets its route (`routeOutgrown`), auto-layout resets all routes, and both are undoable.
- **Tree editor (Phase 4, edit mode only):** a toolbar picks the `Tool` (`select`, `add`, `connect`, `delete`) that decides what a canvas click does. To add a tool, extend `Tool` and handle it in `onNodeActivate`, `onCanvasClick` and `onEdgeClick`. Every edit is saved immediately. Moves and threshold changes replace the one node from the response, while structural changes (nodes or edges added or removed) call `reloadContents()`. Dragging uses mouse events with a 3-unit threshold before a press counts as a drag, and freezes the view box during the drag. `toCanvasPoint` converts screen coordinates with `getScreenCTM`, falling back to unscaled coordinates in jsdom. `AddNodePanel` places an existing library node or creates and places a new one.
- **Routing:** route and query params bind to component `input()`s (`withComponentInputBinding`), so components read `id()` and never inject `ActivatedRoute`. `TreeView` and `NodeView` load from an `effect` on `id()`, because a link to another tree or node reuses the component.
- **Tests:** Vitest in jsdom through `ng test`, with Jasmine-style `describe`/`it`/`expect` globals and `vi` for spies. HTTP goes through `HttpTestingController`. Because the app is zoneless, call `await fixture.whenStable()` after flushing a request or changing inputs.

## Domain model (from the plan)

- The schema supports multiple users from the start: data is owned by a `user_id`. The v1 experience is still single-user.
- **Node:** lives in a per-user library, independent of any tree. It has a title, description, a hand-entered readiness value (integer 0–100) and an ordered list of resources (Phases 7.2 and 7.3): URLs, for reading only, and trees, flashcard decks, external materials, lessons and coding question sets, which count toward readiness unless marked reference-only. Its readiness is the average of the resources that count (a tree is the average of its nodes, a deck the share of its cards passed, a material or lesson the latest progress entered, a question set the share of its questions solved); the hand-entered value is used only when none count, and kept otherwise. A node can count several of each. Trees can nest through these links, but never in a loop. Node detail views show both its prerequisites and the nodes that depend on it.
- **Tree:** an arrangement of library nodes, with category, tags and description. The same node can appear in several trees.
- **Readiness levels** (computed client-side in `trees/readiness.ts`, Phase 5.5): a tree node is **ready** when it has no prerequisites, or when its prerequisites' readiness averages at least its `aggregateThreshold` and each one is at least its `individualThreshold`. Otherwise its progress is the lower of (average / aggregate threshold) and (weakest / individual threshold), shown as one of three more levels: **not started** (below 25%), **early** (25–75%) and **close** (75% up to ready). Each level has its own fill, border style and label (`READINESS_LEVELS`), with a legend on the tree page. Its own readiness doesn't count. Prerequisites never feed into readiness itself; only resources that count do.
- **Node tags** (Phase 5.3a): comma-separated in the form, like tree tags, stored in `node_tags`.
- **Tree edit session:** a tree in edit mode, with the restore point taken when "Edit" was clicked. No tree stays in edit mode: leaving discards, and an unfinished session is resolved on the next visit.
- **TreeNode:** the tree-to-node association. It holds the x/y position and the node's two readiness thresholds for that tree: `aggregateThreshold` (default 80, the minimum average of its prerequisites) and `individualThreshold` (default 70, the minimum for each prerequisite). The thresholds are per node, not per edge; the user decided this in Phase 1. A node shows as "ready" only when both are met.
- **Prerequisite:** a directed edge (`prerequisite` → `dependent`) between two TreeNodes in the same tree. The database blocks self-edges and duplicate edges. The same-tree rule and cycle prevention are enforced in `PrerequisiteService`, and the client checks for cycles too.
- **Deck, Card, CardReview** (Phase 7.1): a deck belongs to a user and has cards (front and back). Each answer is a `CardReview` (user, time, correct or wrong) that's never changed; the user grades their own answers. Decks are studied from their own pages and the review page, and feed a node's readiness when it lists them (7.3).
- **Material, MaterialProgressUpdate** (Phase 7.4): a material is a URL with a title and notes, owned by a user. The user reports progress on it (0–100, with an optional note); every report is kept, and the latest is the material's progress, shown as self-reported.
- **Lesson** (Phase 7.5): written in the app as ordered Markdown sections. Its progress is entered by hand (self-reported, the latest counts), and "last reviewed" is when the user last opened it to read; both are kept per user.
- **QuestionSet, CodingQuestion, QuestionAttempt** (Phase 7.6): written coding problems (HTML or CSS) solved on the user's own machine, grouped into sets. A question is 0% or 100%: solved once marked so. Revealing the solution is recorded, and whether it came before solving is kept for later.
